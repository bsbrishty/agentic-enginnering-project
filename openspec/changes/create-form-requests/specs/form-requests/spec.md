# Capability: form-requests

The Form Request validation classes for the Testimonial SaaS application. This delta spec defines the contract for input validation, derived from `docs/data-model.md` §8. After this change archives, it merges into `openspec/specs/form-requests/spec.md`.

Scope: **column-level** validation. Cross-cutting business rules (plan-limit enforcement, the consent invariant, conditional `rating`) are enforced at the controller, service, or policy layer and are explicitly out of scope here.

## ADDED Requirements

### Requirement: StoreSpaceRequest validates space creation input

The system SHALL provide a `StoreSpaceRequest` class at `App\Http\Requests\StoreSpaceRequest` extending `Illuminate\Foundation\Http\FormRequest`.

The class SHALL implement `authorize()` returning `true` (route middleware handles access control).

The class SHALL implement `rules()` returning the following validation rules:

- `title`: `required|string|max:255`
- `subtitle`: `nullable|string|max:255`
- `collection_question`: `required|string|max:5000`
- `theme`: `required|in:minimal_light,modern_dark,warm_friendly`
- `rating_enabled`: `required|boolean`
- `fields_config`: `required|array`

The rules SHALL NOT include `public_slug` or `public_token`; these are auto-generated by the `Space` model on create (see `docs/data-model.md` §3.2 and the `eloquent-models` spec). The rules SHALL NOT include `user_id`; it is set by the controller from the authenticated user.

The class SHALL NOT override `messages()` or `attributes()`; Laravel defaults apply.

#### Scenario: Valid space creation passes

- **WHEN** a POST request is made to the create-space endpoint with all required fields present and valid
- **THEN** `StoreSpaceRequest::rules()` evaluates to a passing rule set
- **AND** `$request->validated()` returns the validated payload
- **AND** the controller can use the payload to instantiate a `Space`

#### Scenario: Missing title is rejected

- **WHEN** a POST request omits `title`
- **THEN** the validator fails with a key of `title`
- **AND** the response is HTTP 422

#### Scenario: Invalid theme is rejected

- **WHEN** a POST request sets `theme = 'neon_pink'`
- **THEN** the validator fails with a key of `theme`
- **AND** the response is HTTP 422

#### Scenario: Public identifiers are not assignable via request

- **WHEN** a POST request includes `public_slug` and `public_token` in the body
- **THEN** the values are ignored by the form request (no rule, no `validated()` key)
- **AND** the `Space` model's `creating` hook generates fresh values that are persisted instead

### Requirement: UpdateSpaceRequest validates space updates and forbids URL changes

The system SHALL provide an `UpdateSpaceRequest` class at `App\Http\Requests\UpdateSpaceRequest` extending `FormRequest`.

The class SHALL implement `authorize()` returning `true`.

The class SHALL implement `rules()` where every rule is prefixed with `sometimes` to allow partial updates:

- `title`: `sometimes|required|string|max:255`
- `subtitle`: `sometimes|nullable|string|max:255`
- `collection_question`: `sometimes|required|string|max:5000`
- `theme`: `sometimes|required|in:minimal_light,modern_dark,warm_friendly`
- `rating_enabled`: `sometimes|required|boolean`
- `fields_config`: `sometimes|required|array`

The rules SHALL NOT include `public_slug`, `public_token`, or `user_id`. These are immutable per data-model §3.2 and the round-1 grill decision that URLs are not rotated by the owner.

The class SHALL include a docblock stating the immutability constraint and warning that controllers must not pass these fields to the model.

#### Scenario: Partial update changes only the title

- **WHEN** a PATCH request is made with `{title: 'New Title'}` and no other fields
- **THEN** the validator passes
- **AND** the model's `title` is updated
- **AND** `public_slug` and `public_token` retain their original values

#### Scenario: Empty body is accepted by partial update

- **WHEN** a PATCH request is made with an empty body
- **THEN** the validator passes (no `required` fields are missing because all rules use `sometimes`)
- **AND** no model fields are updated

#### Scenario: Invalid theme on update is rejected

- **WHEN** a PATCH request sets `theme = 'neon_pink'`
- **THEN** the validator fails with a key of `theme`
- **AND** the response is HTTP 422

#### Scenario: Public slug and token are not modifiable

- **WHEN** a PATCH request includes `public_slug` or `public_token` in the body
- **THEN** the values are ignored by the form request
- **AND** the model's existing values are preserved on update

### Requirement: StoreTestimonialRequest validates public submission form input

The system SHALL provide a `StoreTestimonialRequest` class at `App\Http\Requests\StoreTestimonialRequest` extending `FormRequest`.

The class SHALL implement `authorize()` returning `true`. The public submission endpoint is open; per-space rate limiting, spam protection, and consent-aware eligibility are enforced at middleware/policy/controller layers, not here.

The class SHALL implement `rules()` returning the following validation rules:

- `submitter_name`: `required|string|max:255`
- `submitter_email`: `required|email|max:255`
- `submitter_company`: `nullable|string|max:255`
- `submitter_social_links`: `nullable|array`
- `submitter_social_links.*`: `nullable|url|max:2048`
- `testimonial_text`: `required|string|max:10000`
- `rating`: `nullable|integer|min:1|max:5`
- `profile_photo_url`: `nullable|url|max:2048`
- `field_values`: `required|array`
- `consent_state`: `required|in:granted,declined,not_asked`

The rules SHALL NOT include `space_id` (resolved from the route), `submitted_at` (set by the controller), or any of the owner-only flags (`is_favorite`, `is_wall_of_love`, `is_hidden`).

The class SHALL include a docblock stating that the form request validates the *value* of `consent_state`, not its policy implications; the controller/policy layer enforces that `consent_state = 'granted'` is required for Wall of Love eligibility per data-model §6.

#### Scenario: Valid public submission passes

- **WHEN** a POST request is made to `/c/{token}` with a complete valid payload including `consent_state = 'granted'`
- **THEN** the validator passes
- **AND** a `Testimonial` row is created

#### Scenario: Missing consent state is rejected

- **WHEN** a POST request omits `consent_state`
- **THEN** the validator fails with a key of `consent_state`
- **AND** the response is HTTP 422
- **AND** no `Testimonial` row is created

#### Scenario: Invalid consent state is rejected

- **WHEN** a POST request sets `consent_state = 'maybe'`
- **THEN** the validator fails with a key of `consent_state`
- **AND** the response is HTTP 422

#### Scenario: Invalid email is rejected

- **WHEN** a POST request sets `submitter_email = 'not-an-email'`
- **THEN** the validator fails with a key of `submitter_email`
- **AND** the response is HTTP 422

#### Scenario: Rating out of range is rejected

- **WHEN** a POST request sets `rating = 7`
- **THEN** the validator fails with a key of `rating`
- **AND** the response is HTTP 422

#### Scenario: Owner-only flags are not assignable

- **WHEN** a POST request includes `is_wall_of_love = true` in the body
- **THEN** the value is ignored by the form request
- **AND** the persisted `Testimonial` has `is_wall_of_love = false` regardless

### Requirement: StoreEmbedConfigRequest validates embed configuration input

The system SHALL provide a `StoreEmbedConfigRequest` class at `App\Http\Requests\StoreEmbedConfigRequest` extending `FormRequest`.

The class SHALL implement `authorize()` returning `true`.

The class SHALL implement `rules()` returning the following validation rules:

- `layout`: `required|in:masonry,carousel`
- `theme_mode`: `required|in:light,dark`
- `background_color`: `required|regex:/^#[0-9A-Fa-f]{6}$/`
- `animation_enabled`: `required|boolean`

The rules SHALL NOT include `public_id` (auto-generated by the `EmbedConfig` model on create) or `space_id` (resolved from the route).

#### Scenario: Valid embed config passes

- **WHEN** a POST request is made to the create-embed endpoint with `layout = 'masonry'`, `theme_mode = 'light'`, `background_color = '#ffffff'`, `animation_enabled = true`
- **THEN** the validator passes
- **AND** an `EmbedConfig` row is created with a fresh UUID v4 `public_id`

#### Scenario: Invalid background color is rejected

- **WHEN** a POST request sets `background_color = 'red'`
- **THEN** the validator fails with a key of `background_color`
- **AND** the response is HTTP 422

#### Scenario: Invalid layout is rejected

- **WHEN** a POST request sets `layout = 'parallax'`
- **THEN** the validator fails with a key of `layout`
- **AND** the response is HTTP 422

#### Scenario: Public id is not assignable

- **WHEN** a POST request includes `public_id = 'custom-id'` in the body
- **THEN** the value is ignored by the form request
- **AND** the model generates a UUID v4 and overwrites any provided value

### Requirement: Validation contract integrity invariants

The form-request classes, taken together, SHALL respect the data-model invariants defined in `docs/data-model.md` §2. Specifically:

- **Auto-generated fields are not assignable via request input.** `Space.public_slug`, `Space.public_token`, `EmbedConfig.public_id` are not validated and not accepted from input. The model's `booted()` hook is the only source of these values.
- **Immutable fields are not modifiable via update.** `UpdateSpaceRequest` does not include `public_slug`, `public_token`, or `user_id` in its rules; even if a request includes them, they are not propagated to the model via `validated()`.
- **Owner-only flags are not set by the public form.** `StoreTestimonialRequest` does not include `is_favorite`, `is_wall_of_love`, or `is_hidden`; the public submission form cannot promote a testimonial to the Wall of Love.
- **Consent state is a tri-state enum, not a boolean.** `consent_state` is validated as `in:granted,declined,not_asked`. The form request does not collapse the three states into a boolean — that would lose the "asked but unanswered" edge case the data-model spec calls out.
- **No column is silently coerced.** String `true`/`false` for booleans is rejected by Laravel's `boolean` rule; numeric strings for `integer` are rejected; URLs without a scheme are rejected by the `url` rule.

#### Scenario: Form requests do not write to auto-generated columns

- **WHEN** any of the four form requests validates a payload that includes `public_slug`, `public_token`, or `public_id`
- **THEN** the value is not in the validated payload
- **AND** the controller can only set these values by calling the model's generation logic (e.g., explicitly via the `booted()` hook)

#### Scenario: Form requests do not modify immutable fields

- **WHEN** `UpdateSpaceRequest` validates a payload that includes `public_slug`, `public_token`, or `user_id`
- **THEN** the value is not in the validated payload
- **AND** the model's existing values are preserved

#### Scenario: Booleans are validated as actual booleans

- **WHEN** a request sets `rating_enabled = 'yes'` (string, non-boolean-ish)
- **THEN** the validator fails with a key of `rating_enabled`
- **AND** the response is HTTP 422
